# Разработка TaskFlow

Текущая версия: **1.0.0-alpha.1**. Источник номера — [VERSION](VERSION); CI проверяет совпадение номера во frontend, lock-файле и backend.

## Ветки

- `main` — проверенная версия рабочего сервера. Только владелец `sergeiBogdano` принимает PR в эту ветку.
- `develop` — интеграция следующего выпуска; сейчас синхронизирована с main.
- `codex/<задача>`, `feature/<задача>`, `fix/<задача>` — короткие рабочие ветки от актуального develop.

Прямой push, force push и удаление main/develop запрещены серверными правилами GitHub. Настройка действует и для владельца при обычной работе. Как владелец репозитория он сохраняет возможность изменять сами правила; GitHub не может запретить владельцу администрировать собственный репозиторий.

## Обычная задача

```bash
git fetch origin
git switch develop
git merge --ff-only origin/develop
git switch -c feature/short-name
# внести изменения и выполнить нужные проверки
git add <конкретные-файлы>
git commit -m "Описание результата"
git push -u origin feature/short-name
```

Открыть PR **в develop**, описать проблему, результат, проверку и влияние на данные. Каждый PR должен пройти обязательные проверки GitHub. Крупные задачи разбивать на небольшие изменения. После принятия рабочую ветку можно удалить; старые ветки удалять только после проверки, что нужные изменения сохранены.

`CODEOWNERS` запрашивает ревью владельца. Минимальное число формальных approvals пока равно нулю: иначе единственный разработчик не сможет принять собственный PR, потому что GitHub не разрешает самоподтверждение. Контроль выпуска обеспечивается отдельным правилом: в main принимает только владелец. При появлении постоянного второго reviewer можно повысить требование для develop до одного approval.

## Выпуск

1. Обновить номер одновременно в VERSION, dashboard-ui/package.json, dashboard-ui/package-lock.json, dashboard-ui/src/lib/version.ts и taskflow-seo/app/web/app.py.
2. Следующее исправление после исходной альфы — `1.0.0-alpha.2`, затем `.3` и так далее. До готовности не убирать суффикс alpha.
3. Добавить запись CHANGELOG.md и проверить `python scripts/check_project_policy.py`.
4. Принять рабочие PR в develop и открыть релизный PR **develop → main**. Проверка project-policy отклоняет другие источники релизного PR.
5. Дождаться всех обязательных проверок. Владелец проверяет изменения и принимает релиз **merge commit**, чтобы сохранить общую историю develop и main. Squash разрешён для небольших рабочих PR в develop, но не для релиза в main.
6. Проверить CI коммита main и Deploy. Deploy запускается после успешного CI push в main; успешный PR CI сам по себе не обновляет сервер.
7. Создать неизменяемый тег `v<версия>` на проверенном коммите main, не переставлять существующие теги.
8. После выпуска открыть обратный PR **main → develop**, чтобы develop включала релизный merge commit. Не синхронизировать защищённую ветку принудительным push.

В экстренном исправлении рабочая ветка может начинаться от main, но результат всё равно проходит develop → main. Не отключать защиту ради срочности.

## Приглашение разработчика

В GitHub открыть Settings → Collaborators → Add people и пригласить нужный аккаунт. Выдать права работы с кодом, без передачи аккаунта владельца или секретов сервера. Ограничение main привязано к конкретному аккаунту владельца, а не ко всем участникам с write-доступом.

Участник создаёт рабочие ветки и PR в develop. Принятие в main остаётся за владельцем. Для внешнего участника возможен fork → PR в develop. Fork PR не должен получать секреты развёртывания.

## Проверки и секреты

CI проверяет backend, PostgreSQL-сценарии, frontend и зависимости. Проверка project-policy добавляет согласованность версии и направление релизного PR. Backend coverage XML/JSON сохраняется как artifact на 30 дней; это покрытие строк Python app, а не всего приложения.

Полные тесты выполнять на отдельной тестовой базе. Не запускать их с production DATABASE_URL. Не коммитить .env, ключи, резервные копии и пользовательские выгрузки. Изменения миграций требуют отдельного плана совместимости и восстановления.
