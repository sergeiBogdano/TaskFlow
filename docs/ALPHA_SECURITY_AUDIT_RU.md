# Состояние после исправлений, 8 октября 2026

Ниже сохранён исходный аудит предыдущей версии; его формулировки описывают состояние **до исправлений**.

Закрыто в текущем коде: очистка HTML при записи и выдаче, отзыв сессий при выходе,
удаление токена из JSON входа, ограничение попыток входа, проверка Origin,
ограничение тела запроса, чтение файлов порциями, проверка формата изображений,
запрет активных вложений, квота пространства и сжатие изображений на клиенте.
Убраны серверные запросы favicon по произвольным адресам. Добавлены CSP в образ
интерфейса и запуск backend без root. Зафиксированы версии прямых Python-зависимостей.
Повторная проверка установленных Python-пакетов: известных уязвимостей не найдено.

**Уточнение пользователя:** CRYPTO_SECRET на сервере сгенерирован и непустой.
Он не читался и не менялся. Добавлена проверка секретов при запуске и явная ошибка
расшифровки вместо молчаливого исчезновения доступов.

HTTP сохранён по запросу пользователя; COOKIE_SECURE по умолчанию false.
Это не обеспечивает шифрование канала. HTTPS, состояние серверных томов,
резервных копий, firewall и дискового шифрования локальным кодом не проверены.
Ограничение входа хранится в памяти одного процесса; для нескольких серверов нужен
общий ограничитель на reverse proxy. MFA, антивирус вложений и полноценный пентест
не реализованы. Статус остаётся alpha.

Для существующих Docker-томов перед обновлением проверьте доступ UID/GID 10001
к каталогу logs; старые файлы могли создаваться root. Нельзя развёртывать новую
версию без проверки /health и тестового входа. См. руководство по переработке.

# Безопасность и готовность к alpha на реальном сервере

Проверка 7 октября 2026 года, версия `1.0.0-alpha.1`, коммит `3113af9`.
Проверены локальные исходники и отдельная демонстрационная база. Production-сервер,
его внешняя сеть, reverse proxy, реальные ключи и резервные копии не проверялись.
Это целевой аудит, а не заключение о прохождении полного пентеста.

## Подтверждённые проблемы

### 1. Небезопасный вывод комментариев — высокий приоритет

`app/web/api/tasks.py` сохраняет содержимое комментария без очистки HTML.
`dashboard-ui/src/pages/Tasks.tsx` выводит его через `dangerouslySetInnerHTML`.
В локальном прогоне подтверждено сохранение HTML без изменения; использован
безвредный маркер, выполнение атакующего JavaScript не проводилось.

Этот путь допускает stored XSS: HTML из API нельзя считать доверенным только потому,
что обычный редактор предоставляет ограниченный набор кнопок. Последствия зависят
от содержимого и ограничений браузера/proxy. HttpOnly препятствует чтению cookie,
но не запрещает скрипту совершать действия в приложении от имени открывшего страницу.

До использования реальных данных: очищать HTML по разрешённому набору тегов,
атрибутов и URL, проверять все места вывода пользовательского HTML, добавить
сценарии безопасности для комментариев и браузерную проверку. CSP — дополнительная
защита, не замена очистке.

### 2. Выход не отзывает сессию — подтверждено запросом

После `/api/auth/logout` повторный запрос `/api/auth/me` с сохранённым до выхода
токеном вернул **200**. Выход удаляет cookie в браузере, но токен остаётся действительным
до истечения срока или изменения версии сессий аккаунта. Срок — 30 дней.

Нужна определённая политика: отзыв конкретной сессии при выходе, просмотр и отзыв
активных сессий, явный выход со всех устройств. Смена пароля и блокировка уже
используют `session_version` и отзывают старые сессии.

### 3. Cookie без Secure

При входе и смене пароля выставляются HttpOnly и SameSite=Lax, но нет Secure.
Локальный ответ это подтвердил. Также токен повторно возвращается в JSON входа,
хотя браузерная авторизация использует cookie.

Для HTTPS production требуется Secure. Возврат токена в JSON расширяет поверхность
его случайного раскрытия. Фактические правила cookie и принудительный HTTPS внешнего
reverse proxy не проверялись.

### 4. Небезопасные значения ключей по умолчанию

В Settings `WEB_APP_SECRET` по умолчанию пуст, `CRYPTO_SECRET` имеет публично известное
значение. Пустой CRYPTO_SECRET тоже превращается в предсказуемый ключ. Нет проверки,
которая запрещает такой запуск вне тестов. Compose требует заполнить переменные,
но не проверяет их случайность и не защищает запуск другим способом.

Известный ключ подписи позволяет подделывать токены; известный ключ шифрования
лишает смысла защиту клиентских доступов при получении копии базы. Наличие этих
значений на реальном сервере **не утверждается**: его секреты не читались.

### 5. Ошибка расшифрования скрывается

`decrypt_accesses_value` при ошибке пробует старый открытый JSON, затем возвращает
пустой список. Локально подтверждено, что повреждённый шифротекст даёт `[]`.
При неверном ключе это может выглядеть как отсутствие сохранённых доступов.

Нужны различимые ошибки, журналирование без секретов и управляемая миграция старых
открытых записей. Ротация ключа требует повторного шифрования данных, а не простой
замены переменной окружения.

## Риски, обнаруженные по коду, требующие отдельной проверки

- **SSRF при получении favicon.** Сервер делает HTTP/HTTPS-запрос к введённому домену
  через `urlopen`; нет проверки частных/loopback адресов и адресов перенаправлений.
  Возможность обращения к внутренним сервисам зависит от сети серверного окружения.
  Запросы к внутренним сервисам в этом аудите не выполнялись. Есть также внешняя
  загрузка иконок через Google — это не полностью автономный режим.
- **Перебор паролей.** Ограничитель попыток входа, задержки и MFA в приложении не найдены.
  Наличие ограничений на внешнем proxy неизвестно. Root особенно нуждается в защите входа.
- **Файлы.** Размер проверяется после полного чтения файла. Квоты пространства/аккаунта
  и сканирование загрузок не обнаружены. Изображения, включая тип SVG, могут отдаваться
  inline; MIME приходит от загрузившего. Нужны ограничения активных форматов, безопасная
  выдача и проверка нагрузки. Файлы сохраняются в БД, а не пропадают вместе с контейнером.
- **CSRF и защитные заголовки.** SameSite=Lax присутствует, явная проверка Origin/CSRF
  и CSP в рассмотренном приложении не обнаружены. Это не доказательство успешной
  CSRF-атаки. Заголовки внешнего reverse proxy требуют отдельной проверки.
- **Контейнер.** Dockerfile backend не задаёт непривилегированного пользователя.
  Фактический пользователь и ограничения контейнера могут задаваться оператором.
- **Зависимости.** Backend задаёт нижние границы версий, а не фиксированный набор.
  В рассмотренном CI нет проверки уязвимостей зависимостей. Конкретные известные
  уязвимости установленных версий этим аудитом не устанавливались.

## Что с шифрованием

- Пароли аккаунтов хранятся как солёные хэши PBKDF2-HMAC-SHA256, 100 000 итераций,
  сравнение результата выполнено через `hmac.compare_digest`. Это не открытые пароли.
  Параметры и переход на более сильную конфигурацию требуют отдельного планирования.
- Клиентские доступы шифруются библиотекой Fernet. Шифрование и обратное чтение
  подтверждены без вывода реальных секретов.
- Сессии подписываются HMAC-SHA256; подпись не является шифрованием токена.
- Всё приложение не зашифровано целиком: обычные задачи, комментарии, CRM-данные и
  вложения сохраняются в БД в доступном серверу виде. Шифрование диска, бэкапов,
  соединения с БД и HTTPS на внешней границе по локальному коду не подтверждается.
- Пароль root уже закрыт для изменения через интерфейс/API; серверная команда
  остаётся предусмотренным способом обслуживания.

## Функциональные блокеры

См. [прогон месяца](MONTH_TRIAL_RU.md): руководитель не видит все задачи в карточке
спринта; задачи регулярного правила без клиента не получают workspace_id; права
управления спринтами не отделены от просмотра; интерфейс модулей расходится с правами
API; закрытие и перенос остатков не оформлены; неверные даты принимаются; сохранённый
порядок полей не применяется к формам. Это проблемы, которые обычные успешные тесты
не выявили.

## Что проверить перед использованием реальных данных

1. Исправить вывод HTML, потерю принадлежности задач пространству и обзор спринтов.
2. Запретить небезопасные production-ключи, настроить отзыв сессий и защищённые cookie.
3. Проверить HTTPS, фильтрацию входа, доступность БД только из разрешённой сети,
   исходящие запросы, загрузки, секреты и реальные полномочия контейнеров.
4. Настроить резервное копирование PostgreSQL и проверить восстановление на отдельной
   базе. `scripts/backup_db.py` копирует только SQLite-файл и не решает эту задачу.
   Резервная копия должна включать нужные для восстановления ключи, защищённые отдельно.
5. Проверить обновление базы с предыдущей версией, откат, многопользовательское
   редактирование и несколько одновременно работающих экземпляров фонового планировщика.
6. Добавить регрессии для найденных случаев, проверки браузера под разными ролями,
   нагрузочный прогон, мониторинг ошибок и проверку зависимостей.

Итог: alpha пригодна для дальнейшего тестирования на демонстрационных данных в
ограниченной среде. Готовность к открытому production с реальными клиентскими
доступами и документами текущим состоянием не подтверждается.

Локальное доказательство: `taskflow-seo/logs/security-trial-results.json`.
Исходный код приложения и рабочая база в этом аудите не менялись.
