Версия: **1.0.0-alpha.1**. Исходный проверяемый коммит приложения: `796a2128`. Аудит проведён по локальным исходникам, изолированной тестовой базе, конфигурациям CI и реальным настройкам GitHub. Не является независимым пентестом или проверкой всех комбинаций настроек.

Рабочая база, Debian, firewall, установленный server deploy script, фактические резервные копии, метаданные Ollama и потребление GPU не исследовались. Ниже отдельно отмечены воспроизведённые ошибки, выводы по исходникам и эксплуатационные ограничения. Пользовательские данные не изменялись.

Проверки: 54 frontend-теста, серверные сценарии задач/защиты и 4 проверки просрочки/календаря. В браузере на синтетических данных проверены две вкладки (форма A сохранилась с workspace_id=1 после выбора 2 во второй вкладке), показ задач при скрытом исполнителе, ошибка загрузки задач и повторный запуск сессии после 503 без ввода пароля. ## Подтверждённые и воспроизводимые ошибки

### A01. Фильтр просрочки раскрывает сведения о скрытых сроках — высокий приоритет

Временный участник с правом tasks и скрытыми deadline/completionDate получил 200 на `/api/tasks?status=overdue&scope=mine` и задачу со статусом todo, отобранную исключительно по скрытой дате. Самих дат в ответе нет, но факт принадлежности к просрочке раскрывает отношение скрытого срока к текущей дате.

Источник: app/web/api/tasks.py, app/core/task_deadlines.py, app/web/middleware.py. Недавняя динамическая просрочка не добавлена в запреты фильтрации по скрытым полям; paginated status_counts также вычисляет overdue по датам.

Исправление: при недоступных исходных полях запретить фильтр динамической просрочки и не выдавать производные числовые показатели, либо определить отдельное явное разрешение на такую производную информацию. Добавить тесты скрытых дат, смешанных статусов и пагинации. Это не подтверждённый доступ к чужому пространству; проблема относится к скрытым полям доступных задач.

### A02. Сегодняшняя задача в календаре красная как просроченная — средний приоритет

В изолированной базе задача с completion_date сегодня в 18:00 и deadline завтра вернулась из календаря с цветом `#dc3545`. В коде `(day_start - datetime.now(tz)).days` после полуночи даёт -1 для сегодняшнего дня.

Источник: app/web/api/calendar.py, вычисление days_until.

Исправление: сравнивать календарные даты в часовом поясе приложения; добавить сценарии сегодня/вчера/завтра, выполненной задачи и границы суток.

### A03. Скрытый исполнитель может убрать разрешённые задачи из интерфейса — средний приоритет

Сервер правильно выбирает задачи для scope=mine, затем убирает assignee_id как скрытое поле. Tasks.tsx повторно фильтрует результат через taskMatchesScope, который сравнивает удалённый assignee_id с пользователем. Разрешённые задачи исключаются, хотя total остаётся положительным.

Подтверждено: API возвращает задачу при скрытом исполнителе; выполнение taskMatchesScope с таким ответом возвращает false. Полный браузерный сценарий этого конкретного профиля отдельно не выполнялся.

Исправление: доверять серверной выборке и не повторять проверку принадлежности по скрытым данным на клиенте. Серверную авторизацию сохранить.

### A04. Выбор пространства разделяется вкладками без согласованного обновления интерфейса — высокий приоритет целостности

WORKSPACE_KEY хранится в localStorage. request() читает его при каждом запросе. switchWorkspace() перезагружает только текущую вкладку; другие вкладки не обрабатывают storage-событие.

Клиентский сценарий воспроизведён с перехватом fetch, без записи на сервер: в A подготовлена форма создания задачи пространства A; в B выбран B; вызов createTask с подготовленным в A текстом отправил POST /api/tasks?workspace_id=B. Если пользователь имеет права в обоих пространствах, сервер может законно принять запись в B, хотя форма показывала A. Изменение существующей задачи дополнительно защищено её фактическим workspace_id; не утверждается, что этот путь позволяет менять чужие объекты.

Исправление: привязать пространство к вкладке или явно закреплять workspace_id за открытой формой; при внешней смене пространства показывать уведомление и сохранять несохранённый текст. Добавить тест двух вкладок и создания объекта.

### A05. Ошибка API задач не получает собственного понятного состояния — средний приоритет

Tasks.tsx запускает load().finally(setLoading(false)) без catch в загрузке страницы. При отказе в доступе, сетевой ошибке или неправильном фильтре возможны пустой список, старые данные либо unhandled rejection. React error boundary не ловит ошибки Promise.

Исправление: отдельные loading/error/empty состояния, повторная загрузка по кнопке и защита от устаревших ответов. Не показывать ошибку как «задач нет».

### A06. Восстановление входа трактует любой сбой как выход — средний приоритет

AuthProvider начальная цепочка getMe/ensureWorkspace/getMe ловит любую ошибку и очищает user/account. Временная ошибка сети или 500 показывает вход вместо возможности повторить запуск; сам запрос fetch не имеет общего ограниченного времени ожидания.

Исправление: отличать 401 от сетевых/серверных ошибок; предусмотреть таймаут и retry, не запускать автоматический бесконечный цикл.

## Ограничения архитектуры и удобства

1. Скрытие одного поля отключает dashboard/reports/modules; поиск, историю и некоторые другие производные API middleware блокирует целиком. Это защитное ограничение, а не подтверждённая утечка поиска. Пользователю трудно связать исчезновение раздела с профилем полей. Требуется показывать точную причину и постепенно считать безопасные сводки.
2. NoteFolder и SavedView не привязаны к workspace; папки и сохранённые представления принадлежат аккаунту. Это не доступ к чужим пользователям, но настройки окружений смешиваются и требуют явного объяснения или модели привязки.
3. Локальные заметки остаются в браузере/выбранной папке, не синхронизируются автоматически и не входят в серверную копию. Потеря профиля браузера может уничтожить единственную копию. Нужен понятный экспорт и проверенная процедура восстановления.
4. Серверный список заметок отдаёт полное содержимое всех доступных записей без пагинации. Middleware также собирает JSON-ответ в память для очистки. Большие объёмы заметок увеличат память и время загрузки; нужны отдельные списки метаданных и загрузка содержимого по запросу.
5. ИИ получает ограниченную выборку и обрезанные фрагменты, а не всю базу. Контекст 4096 может быть меньше подготовленного JSON; точный токен-бюджет перед запросом не рассчитан. Дата фильтра — текущее состояние выбранных записей, а не восстановление истории.
6. Установленная модель с суффиксом `_ru` закреплена в Compose, поэтому изменение OLLAMA_MODEL в серверном .env не переключит её. Метаданные и базовая модель локального тега неизвестны без Debian-проверки. Это выбранная настройка последних коммитов, не вывод о фактическом качестве модели.

## Надёжность и безопасность эксплуатации

- Миграции запускаются при старте и некоторые ошибки только журналируются, после чего запуск продолжается. /health проверяет SELECT 1, а не полноту схемы. Нужны версионированные миграции и отказ запуска при обязательной миграционной ошибке.
- scripts/backup_db.py уже поддерживает PostgreSQL через pg_dump и SQLite через backup API. Прежнее утверждение, что он только для SQLite, устарело. Но Dockerfile backend не устанавливает pg_dump: доступность клиента на месте выполнения нужно подтвердить.
- Шифрование резервной копии читает весь файл в RAM и создаёт дополнительные буферы. Для большой базы это риск памяти; нужна стратегия резервирования, подходящая реальному размеру данных. Фактические расписание и восстановление не проверены.
- Секреты клиентских доступов и резервных копий шифруются; все задачи, заметки, комментарии и вложения не зашифрованы целиком при хранении. MFA и отдельные управляемые сессии по устройствам отсутствуют; logout отзывает все сессии аккаунта.
- Общая очередь ИИ ограничивает обработку запросов, но CPU/RAM/GPU самого Ollama определяются серверной конфигурацией, не проверенной локальным аудитом.
- Требуются реальные проверки firewall, служебных портов, прав служб, резервных копий, мониторов и восстановления после неудачного обновления. Успешный Deploy сам по себе не доказывает эти свойства.
