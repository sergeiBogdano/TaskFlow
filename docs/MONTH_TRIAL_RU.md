# Исправления после месячного прогона, 8 октября 2026

Сохранённый ниже отчёт описывает предыдущую версию.
В текущем коде исправлены права просмотра спринтов, отдельное разрешение
планирования, обратные даты, принадлежность задач генератора пространству,
перенос между активными спринтами и явное решение о незавершённых задачах
при закрытии. Действия и поля защищены серверными профилями и личными исключениями.

Повторения отдельных задач через устаревшие recurring-параметры не поддерживаются;
создание больше не игнорирует их молча, а направляет в модуль автоматизации.
Статус «На проверке» остаётся рабочим статусом, без обязательного процесса утверждения.
Глобальная перестановка всех полей между группами карточки не реализована;
имеется порядок полей внутри существующих групп.

Это не подтверждает месяц непрерывной работы production-сервера.

# Практический прогон месяца работы

Проверка версии **1.0.0-alpha.1**, коммит `3113af9`, выполнена 7 октября 2026 года.
Смоделирован ноябрь 2026 года в отдельной локальной базе. Это ускоренное
воспроизведение действий пользователей, а не месяц наблюдения за работающим
сервером. Даты задач заданы вручную; фактический ход времени не ускорялся.

## Как организована работа

- Пространство «Студия»: руководитель, дизайнер, разработчик и проверяющий.
- Отдельное пространство «Учёба»: тот же разработчик, задачи без CRM.
- Дополнительный посторонний аккаунт для проверки изоляции.
- Один заказчик, договор поддержки и связанная CRM-сделка.
- Четыре недельных спринта: план и макеты; разработка; проверка; сдача и продление.
- В каждом спринте шесть задач: планирование, макет, реализация, проверка,
  обратная связь и сдача. Всего **24 основные задачи**.

Вход выполнялся отдельно под каждым аккаунтом. Назначенные исполнители переводили
задачи в работу, на проверку и в завершённые; часть задач оставлена в ожидании и
в работе. До дополнительных проверок каждый спринт показывал **4 из 6, 67%**.
Один незавершённый результат добавлен во вторую неделю. Проверены продление договора,
архив сделки, корзина задачи, восстановление, повторение и генерация задач правилом.

Браузерная часть проведена под руководителем пространства: просмотр спринтов,
карточки спринта, модулей и настроенных подписей. Основной объём данных подготовлен
и проверен через локальный API; это не замер времени ручного ввода каждой карточки.

## Что получилось

1. Создание независимых пространств и работа одного аккаунта в двух командах.
2. Назначение задач разным исполнителям и изменение статусов этими исполнителями.
3. Постороннему аккаунту отказано в доступе к задачам студии; задачи другого
   пространства нельзя добавить в её спринт.
4. CRM учебного пространства отключена, в том числе для root.
5. Подсчёт прогресса по завершённым задачам работает. Корзина исключает задачу из
   расчёта, восстановление возвращает её.
6. Продление договора создаёт связанную задачу с правильным договором; архивирование
   сделки сохраняет эту задачу.
7. Изменённое название «Заказчики» видно в меню, подпись «Результат недели» — в спринте.
   Настройки названий и порядка полей сохраняются в конфигурации пространства.

## Что мешает работе

| Приоритет | Воспроизведённый результат | Последствие |
|---|---|---|
| Высокий | Руководитель видит 25 задач в общем списке, но внутри каждого обычного спринта — только свою одну задачу при прогрессе по всем шести. | Нельзя нормально контролировать командный спринт. Проверка видимости в карточке не учитывает рабочие права руководителя. |
| Высокий | Недельное правило без клиента сообщает о создании четырёх задач, но список пространства не показывает ни одной. В локальной базе у всех четырёх `workspace_id = NULL`. | Внутренняя регулярная работа теряется из списка своего пространства. |
| Высокий | Участник с базовыми правами меняет цель спринта: API возвращает 200. | Нет отдельного настраиваемого права «управлять спринтами» при сохранении права просмотра. Это недостаток модели полномочий, а не проверка запрета, уже существующего в настройках. |
| Средний | Руководитель пространства создаёт правило через API, но в интерфейсе модулей отсутствуют кнопки создания и изменения. | Интерфейс проверяет глобальную роль вместо фактических рабочих прав. |
| Средний | Спринт завершается при 67% готовности без предупреждения и решения судьбы оставшихся задач. | Закрытие периода не помогает обработать незавершённую работу. Закрывать неполный спринт допустимо, но нужен явный итог и перенос остатков. |
| Средний | Добавленная во вторую неделю задача остаётся и в первой. | Операции «перенести остатки» нет; добавление в несколько спринтов не равнозначно переносу и меняет историю прогресса. |
| Средний | API принимает спринт с окончанием раньше начала. | Можно сохранить некорректный период, несмотря на ограничения поля даты в браузере. |
| Средний | Порядок полей сохраняется, но формы задач и спринтов не используют возвращаемый `order` для размещения полей. | Настройка порядка создаёт ожидание, которое форма не выполняет. |

Дополнительный сценарий: обычный API создания задачи игнорирует параметры
`recurring_interval` и `recurring_count`; завершение такой задачи не создаёт следующую.
В интерфейсе задачи нет полноценной настройки повторения. Повторение предусмотрено
через отдельные модули; их работу нельзя считать заменой повторяющейся карточки задачи.
Автоматическое срабатывание расписания в будущие календарные даты в этом прогоне
не проверялось: запуск генерации был ручным.

Статус «На проверке» также не является обязательным согласованием: исполнитель
сам перевёл собственную задачу из него в «Готово». Для строгой приёмки нужен отдельный
проверяющий и право подтверждения результата, а не только название статуса.

## Насколько можно настроить приложение

Можно выбрать модули пространства, членство, ранги и рабочие профили, переключатели
функций, видимость пространства, подписи и часть видимости полей, тему и меню.
В CRM есть собственные поля и настраиваемые воронки.

Полноценного конструктора произвольных процессов пока нет. Фиксированные статусы
задач не превращаются в собственный процесс согласования; свободная иерархия
«проект → этап → подзадачи», оценка загрузки по трудозатратам и автоматический перенос
остатков спринта не предоставлены как законченный рабочий сценарий. Настройки форм
требуют проверки применения, а не только сохранения значений.

## Вывод

Для простого личного списка и ручной организации небольшой команды основа подходит.
Для удобного месяца командной работы текущую alpha нужно доработать: сначала
видимость задач руководителем, принадлежность автоматически созданных задач
пространству и права управления спринтами; затем закрытие периода, переносы,
приёмку и применение настроек форм. Заявление «всё настраивается и все сценарии
готовы» этот прогон не подтверждает.

Результаты и демонстрационные данные сохранены локально в `taskflow-seo/logs`:
`month-trial-results.json`, `month-trial.db`, `run_month_trial.py` и снимок
`month-trial-sprint-detail.png`. Пароли и рабочая база существующей установки
не изменялись. Исходный код приложения в этом аудите не исправлялся.
